# 日常开发流程与验收

> 适用于当前维护；早期“恢复基准 → 搭宿主 → 迁移业务”的一次性阶段已经结束。
> 全局边界见 [AGENTS.md](../AGENTS.md)，模块细则由对应 README 维护。

## 工作顺序

1. 查看工作区差异，定位本次任务的模块，保留用户已有修改。
2. 阅读模块 README，查看目标源码和相关测试。仅当接口、数据或事件跨边界时补读契约。
3. 明确要改变的行为及必须保留的不变量；普通局部修改无需另写设计文档。
   新增跨模块协议、修改结算时序或数据模型时，先在对应文档说明接口、失败行为与验证方法。
4. 实施最小完整改动。配置变动附默认值/校验；schema 变动附实体、迁移和恢复路径。
5. 按下表验证，检查 diff 和文档链接；交付时说明变化、验证结果和实际未验证项。

## 分支、同步与任务收尾

本仓库只保留 `main` 作为长期主线，跟踪 `origin/main`；`origin` 是维护仓库
`301zrg/srvprotianti`，`upstream` 仅用于核对上游来源。生产版本由固定提交、发布标签和
批次回执确定，合入 `main` 不自动代表已经部署。`restructure2` 在迁入主线后退役。

- 开工先核对当前分支、上游、工作区和 `git fetch origin` 的结果。常用目录平时保持在
  已同步的 `main`；从最新主线创建 `feat/<功能>`、`fix/<问题>`、`docs/<主题>` 或
  `chore/<事项>`。日期可按需附加，不以工具或执行者名称代替任务用途。
- 每个任务分支跟踪远端同名分支；禁止把功能分支的 upstream 设置为 `origin/main`
  或另一功能分支。上游更新通过显式合并或变基处理，不能借默认 push 更新别的分支。
- 单个任务优先在常用目录完成；只有并行工作或需要冻结候选时增加 worktree。
  记录任务与目录，结束时一并清理。未提交修改先辨认来源并保存，不执行盲目的
  `reset --hard`、`clean`、强制切换或整目录覆盖来制造“已同步”。
- 正常交付闭环是：按影响验证、提交、推送任务分支、通过 PR 合入、更新本地 `main`，
  再清理临时分支和 worktree。干净且没有本地独有提交的主线使用 `git pull --ff-only`；
  出现分叉时先核对原因。缺少合入授权或仍有待审工作时明确说明停在哪一步。
- 删除前确认提交已合入或有经核对的归档标签、未提交和未跟踪内容已有去向，且目录
  不再被未完成的发布批次或页面发布器引用。先推送并回读 `archive/<日期>/<旧分支名>`
  标签，再清理对应远端和本地分支；归档标签保持不可变。本机未审核的 WIP 单独保留，
  不将私有配置、数据库、录像和运行回执混进公共提交。
- `main` 应禁止强推和删除，常规变更通过 PR 与实际存在的检查汇入；仓库保护设置的
  生效状态须单独核对，不能由这份文档推定。发布审批和监控空闲屏障继续沿用运维手册。

## 按影响选择验证

以下命令均在项目根目录执行，机器人行也可直接在根目录执行。
测试入口以各自 `package.json` 为准；不要把历史“测试通过”当作本次证据。

| 改动 | 必要验证 |
| --- | --- |
| 仅 Markdown | 检查相对链接、路径、命令与当前文件一致；`git diff --check`；无需构建或启动服务 |
| 页面文字、样式、JSON 展示配置 | 检查语法/JSON；浏览器核对受影响页面、多语言和移动端；涉及行为时补对应测试 |
| 单个原生 JS 插件内部逻辑 | `node --check <修改的JS文件>`，运行模块 README 指定的现有测试 |
| CoffeeScript 或 TypeScript | `npm run build`（已含 `tsc` 类型检查），检查生成差异，并运行受影响测试 |
| 宿主、共享服务、跨插件接口/事件 | `npm test`；有源文件变化时先构建。检查无插件、缺失依赖及失败路径 |
| 数据结构、迁移/回填 | 映射与集成测试；隔离测试库预检/模拟/验收及恢复演练；不能以生产库充当测试库 |
| 独立机器人 | 分别运行受影响的 `npm --prefix services/bot-core test`、`npm --prefix services/qq-bot test` 或 `npm --prefix services/discord-bot test`；旧合并服务仅在维护它时运行 `npm --prefix services/community-bot test` |

目前多个插件共用 `plugins/tests/plugin-tests.js` 和 `plugins/tests/integration.test.js`，
因此单模块测试也可能覆盖多个插件。不要编造不存在的单插件 npm 命令。
测试通过后，仅在新修改、失败或未消除疑点需要时扩大验证。
只需检查类型而暂不生成文件时，可单独运行 `npx tsc --noEmit --pretty false`；成功构建后无需重复运行。

## 高影响改动补充场景

- 协议/房间/重连：有效席位、G1/G2/G3、两侧消息先到顺序、异常退出、断线座位保护；
  TT 双方超时与普通房行为分别验证。自动测试不能替代两个真实客户端验收。
- 结算/统计：幂等、事务失败、两条镜像、G1 类型冻结、先后攻、同/不同卡组、
  缺失录像、脏数据排除及分母；按所改语义选择样本，不要求无关修改重复全部场景。
- HTTP/下载/权限：参数边界、允许与拒绝路径、公开/认证可见性、路径穿越、
  请求被认领后响应结束，原管理接口鉴权保持。
- 插件机制：使用测试临时目录或隔离副本检查空插件和移除依赖；不要删除工作区插件来做验证。

## 文档与交付

- 行为或使用方式变化时更新所属模块文档；纯内部整理且契约不变时不必同步多份说明。
- 接口提供者维护接口，消费者只记录所依赖的字段及链接；跨模块约定只在契约文档维护详细定义。
- 只有项目级状态、上线前置条件、未解决问题或延期决策变化才更新交接。
- 构建可能触及已有生成文件，提交时逐项核对；不要为清理 diff 覆盖用户改动。
- 明确区分“代码已实现”“本次本地测试通过”“真实平台/客户端通过”“生产已上线”。
  未运行的验证如实写明原因，不继承旧交接中的成功结论。
- 生产迁移和部署按任务中的明确授权及具体手册进行。编写脚本、提供命令或本地模拟不等于授权正式执行。

### 发布来源与收敛

- 发布到正式服的文件必须能追溯到不可变的提交或标签，并附制品清单（发布批次的 `manifest.json` 记录文件、SHA 和线上旧 SHA）。
- 允许从审核过的任务分支或补丁发布。但要记录它与 `main` 的差异，并安排回收到 `main`。
- `main` 是收敛目标，不要求生产始终等于最新 `main`。不能因为 `main` 较新，就整仓覆盖线上已有的修复。部署前先比对线上与候选的逐文件差异。
- 只存在于本机的提交或标签不能作为唯一副本：发布前推送到远端，或另行留存可追溯的副本。
- 现行文档中的跨仓库链接指向 `main`；固定证据指向不可变提交或标签。临时目录不能作为当前操作的唯一依据，尚未迁出的历史证据要注明日期和状态。

### 依赖与契约说明

- 吸收上游（mycard/srvpro、DarkNeos/neos-ts 等）按单项选择：记录固定的来源提交、许可证、兼容性、测试，以及与本地的差异，不整仓覆盖。不改变 1103/706 规则或 TT 认证与结算，也不顺带启用原本没要求的功能。
- 数据库支持范围：正式业务只用 PostgreSQL；SQLite/SQL.js 只用于测试，测试能证明配置和逻辑，不能证明真实事务、并发或迁移；MySQL 只保留历史兼容。
- 缓存、队列等异步能力要在模块文档写明失效时的行为：提交后如何作废、并发请求怎样合并或隔离、失败时如何退化。
- 改动存储位置、权限或环境身份时，同步更新入口摘要和[交接](PROJECT_HANDOFF.md)中受影响的条目。
- 插件 manifest 的 ID 必须唯一。可选服务缺失、插件禁用等组合要有检查；钩子与宿主依赖的目录见[插件入口](../plugins/README.md#钩子目录)。
- 交接中的状态每类只在一处维护，不手抄完整的 dirty 列表或全部 PR 状态；历史决定不在每份功能文档里重复叙述。

## 架构影响与图文同步

每次改动先判断是否改变模块职责/依赖、进程或信任边界、启动/协议/结算时序、事务与数据所有权、
持久化/恢复方式、配置来源或构建/发布链路。任一关系变化，即使代码量很小，也属于架构影响；
在同一交付中更新 [ARCHITECTURE.md](ARCHITECTURE.md) 对应 Mermaid 图、源码入口及说明，
同时核对接口提供者和实际消费者的契约。图只表示已实现关系，方案和未验收状态须另行标明。

文案、样式、模板内容或不改变上述关系的局部修复，只维护所属模块文档；图仍准确时保留，
不为记录改动而重画。已有文档合理且涵盖本次行为时可以不修改。
交付简述“是否影响架构、更新/保留哪张图及依据”，不另建每次修改的永久流水账。
文档验证检查相对链接、图语法与 diff；运行验收仍按前文的改动范围选择。
