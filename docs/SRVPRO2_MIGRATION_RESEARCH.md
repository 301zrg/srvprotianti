# srvpro2 评估与迁移调研归档

> 调研日期：2026-09-16。状态：长期延后，不是当前重构目标。

## 结论

srvpro2 在新项目基础、TypeScript 类型约束、事件/中间件结构、每桌 Worker 隔离以及直接使用 WASM ocgcore 等方面更现代；这不等于它对当前 1103 生产环境已经“无条件更好”。当前 srvprotianti 已有的天梯、历史数据、公开 API、页面、录像关联和运维流程都围绕 srvpro 形成，迁移属于高难度重写，不是替换入口文件即可完成。

建议继续稳定当前 srvprotianti，把 srvpro2 作为未来平台候选。只有在 1103 所需核心/WASM、协议兼容、重连与录像语义、Windows/Linux 生产运行都验证后，再启动独立迁移项目。

上游项目：[purerosefallen/srvpro2](https://github.com/purerosefallen/srvpro2)。

## 相对优势

- TypeScript 为消息、房间和功能模块提供更清晰的类型边界。
- 直接 WASM 核心和每场对局 Worker 隔离，架构上更容易控制单桌故障与并发状态。
- 事件和 middleware 更适合新增横切功能，减少在巨型服务器流程中插入分支。
- PostgreSQL、录像和重连等能力在新架构中被重新设计，而不是继续叠加历史兼容层。

## 当前风险

- 项目较新、发布基线和升级承诺尚不稳定。
- `plugins/` 尚不足以证明存在与本项目 manifest/依赖/服务契约等价的成熟插件生态；现有功能更多位于 `src/feats`。
- 1103 所需 ocgcore、旧客户端协议、卡片脚本和录像兼容是先决闸门。
- 当前项目的生产数据、计分结算边界、录像—对局关联和公开 API 不能原样搬运。

## 迁移难度分层

- 可较多复用：HTML/CSS、翻译文本、卡组模板/元数据、纯计算函数、API 契约和测试样例。
- 需要适配：数据库实体与查询、HTTP 路由、配置加载、房间/消息事件、认证和重连事件。
- 基本重写：宿主钩子适配、天梯完整结算状态机、录像持久化关联、后台投影队列、插件生命周期集成。

整体评估为高难度。合理路径是先做兼容性原型和双写/离线对账，而不是在生产库上原地升级。

5. 保持旧服务器只读回退能力，完成一段时间的影子流量/双系统核对。
