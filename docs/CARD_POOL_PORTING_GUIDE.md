# 其他卡池部署适配指南

本项目按“一个实例只服务一个卡池”设计。不同卡池应使用独立配置、数据库（或至少独立 schema）、录像目录和部署目录，不在同一实例中混合统计。

本文重点列出本项目相对普通 SRVPro 新增功能中的卡池绑定内容。YGOPro 服务端核心、卡片脚本、卡片数据库和禁限卡表仍是搭建任意 YGOPro 服务器的基础前提，此处不重复基础部署教程。

## 1. 推荐：把卡池差异集中为环境包

建议将当前 1103 内容视为一个环境包。环境包不必成为运行时插件，可先作为一组可审查、可复制的配置与静态资源：

```text
environments/
└─ ocg-201103/
   ├─ deck-analysis/       卡组分类元数据、展示分组和模板
   ├─ example-decks/       示例卡组元数据与 ydk
   ├─ web/                 介绍、标题等环境文案配置
   ├─ tips/                入场提示
   └─ ladder/              模式名、欢迎语和规则说明
```

当前代码尚未自动从这个目录安装环境包；第一次迁移其他卡池时可以按下文文件清单替换。以后若实现安装命令，应执行“校验—备份—复制—生成部署摘要”，避免把不同环境内容混在一起。

## 2. 必须重点检查的项目新增内容

### 2.1 卡组分类与展示

位置：`plugins/deck_analysis/`

- `deck_analysis.json`：卡组类型 ID、代码、分支/家族关系和多语言名称。
- `deck_display.json`：统计页面的显示分组及排序。
- `deck_templates/*.ydk`：识别模板；支持 `<类型ID>.ydk`、`<类型ID>-<序号>.ydk`、
  `<类型ID>_<序号>.ydk`，同一类型的任一模板全部命中即返回文件名开头的数字 ID。实际卡组仍须
  包含该模板的全部主卡组和额外卡组卡片，副卡组不参与。
- `config.default.json` / 本地 `config.json`：模板和元数据文件位置、`otherDeckTypeId`。

换卡池时必须重新审查全部模板。不要只改名称：模板里的卡号与最小卡片集合决定历史对局的分类结果。修改分类规则后，旧数据不会自动重算；需要按 `plugins/deck_analysis/RECLASSIFY_DATABASE.md` 的显式流程处理。

### 2.2 示例卡组

位置：

- `plugins/ladder-web/example-decks.json`
- `web/example_decks/*.ydk`

元数据、下载文件和页面链接必须一一对应。删除不适用于新卡池的示例，避免玩家下载到超时代卡片或错误禁限数量的卡组。

### 2.3 页面介绍和环境文案

主要位置：`web/intro.html`，同时检查所有公开页面的 `<title>`、页头和说明文字。

至少替换：

- 卡池名称与时间点（当前为 OCG 2011.03）。
- 服务器地址、端口、加入方式和脚本下载地址。
- 环境特有规则、代表卡片链接和服务器能力说明。
- 页面中的天梯入口、示例卡组说明及任何社群联系方式。
- `intro.html`、`rooms.html`、`ladder.html`、`player-stats.html`、`replays.html`、`deck-stats.html`、`deck-detail.html`、`usage-stats.html` 的网站标题。

建议下一步把这些重复标题和环境文案改为同一份 Web 环境配置；在完成该重构前，用全文搜索卡池年份、服务器 IP、端口和模式代码做人工兜底。

### 2.4 房间提示

位置：`config/tips.json`。

逐语言检查卡池名称、群号、命令说明、服务器规则和链接。`/tip`、语言切换等通用命令可以保留，但环境相关内容必须随环境包替换。

### 2.5 天梯规则

位置：

- `plugins/ladder-core/config.default.json`（本地可由同目录 `config.json` 覆盖）。
- `plugins/ladder-core/i18n.json`。
- `web/intro.html` 及天梯相关页面的规则说明。

检查模式代码、欢迎语、密码要求、初始分、计分公式、提前投降、开局前匿名、同 IP/受限玩家策略和重连前提。若新环境不用 TT 作为模式代码，还要确认客户端文案和部署说明保持一致。

## 3. 基础环境前提（简表）

以下不是本项目新增逻辑，但缺一不可：

- 与卡池匹配的 YGOPro 服务端核心及协议版本。
- `script/` 卡片脚本和对应卡片数据库。
- 禁限卡表、默认规则、起始 LP/手牌、允许卡片范围。
- WindBot/AI 数据（若启用）。
- 客户端使用相同核心兼容范围、卡片数据和脚本。

## 4. 新卡池上线检查顺序

1. 在独立目录和独立数据库完成基础 YGOPro 对局验证。
2. 替换并审核卡组分类、模板与展示分组。
3. 替换示例卡组、介绍页、标题、房间提示和天梯规则。
4. 全文搜索旧环境标识，例如 `1103`、`2011.03`、旧 IP/端口、旧群号和旧脚本 URL。
5. 运行测试和构建；用真实客户端验证匹配、计分、重连、录像、下载和四语提示。
6. 使用空数据库完成一次上线演练；需要导入旧数据时另行设计迁移，禁止跨卡池沿用卡组使用率数据。

## 5. 环境隔离原则

- 每个实例单独保管敏感配置，不把 `config.json` 或密钥纳入环境包。
- 卡组类型 ID 只在本实例/本环境中稳定；不要把两个卡池的同一 ID 当作同一含义。
- 录像依赖生成时的核心、卡片数据和脚本。跨环境展示旧录像时应明确兼容性，不承诺新客户端一定可播放。
- 排行榜和使用率只统计本环境产生的数据；更换卡池相当于新的统计边界。
