### 2026-11-15–16 实验 VM 首装与跨平台恢复

Ubuntu 24.04.5 x86_64、Node 24.15.0、PostgreSQL 17 实验 VM 上，路线 A 首装、路线 B 从 Linux 联合批次恢复均已逐块执行，完成原生引擎构建、配置/权限、systemd 无人登录自启及私网真实客户端验证。路线 A 的真实客户端检查为 8 项，路线 B 为 5 项；这不代表正式服迁移或真人照手册复现完成。路线 B 的 C/C → 内置 C.UTF-8 排序差异已接受，不能推广到中文 locale 源库；中文 locale 源库的实测差异见 [正式库副本迁移演练](#2026-11-16-正式库副本迁移演练windows--linux)。

联合恢复工具另修复两项跨平台缺陷：

- `a5e6691`：Windows psql 的 CRLF 与 Linux 的 LF 曾使同一数据得到不同内容摘要；新批次记录摘要格式，统一记录行尾，旧批次按整库候选匹配。规则及升级风险见 [摘要格式与旧批次](backup-restore.md#摘要格式与旧批次)。
- `0377efc`、`ff13a13`：两平台路径排序不同曾导致同一份文件清单被误拒，改为路径/大小/SHA 的多重集合比较，并受控拒绝畸形清单。文件名和内容要求不变。

以下结果来自两台实验来宾上的独立恢复，每次均使用不同于源库的全新空库和全新目录；只有 restore 退出 0，且 `complete`、`databaseAndFilesVerified`、`replayAssociationsVerified` 三项均为 true 才计为通过。新批次为带摘要格式标识的批次，旧批次无该字段；结果只涉及恢复与只读核对。

| 来源 → 目标 | 结果 | 工具提交 |
| --- | --- | --- |
| 旧 Windows → Linux | 通过，legacy / crlf / whole-batch | a5e6691，ff13a13 复跑 |
| 旧 Linux → Linux | 通过，legacy / lf | a5e6691 |
| 新 Linux → Linux | 通过，新格式严格匹配 | a5e6691 |
| 新 Windows → Linux | 通过，新格式严格匹配 | ff13a13 |
| 旧 Windows → Windows | 通过，legacy / crlf | a5e6691、0377efc、ff13a13 |
| 旧 Linux → Windows | a5e6691 时 verify 被拒；清单顺序修复后通过，legacy / lf，40 组件、14,066 文件 | 0377efc |
| 新 Windows → Windows | 通过，新格式严格匹配 | a5e6691 |
| 新 Linux → Windows | 通过，新格式严格匹配 | a5e6691，ff13a13 复跑 |

同一份数据分别在 Windows 与 Linux 做新格式备份，20 张表的行数与摘要全部一致，整个 `databaseState` 相同。Windows psql → Python 二进制管道实测 78 条记录均为 CRLF、无裸 CR；Linux 同样的 78 条记录为 LF、无 CR。

旧 Windows 批次在 Linux 恢复后，另独立核对了 20 表、276 行、32 对象、12 序列、7 组件、3 录像，12 条所属序列均不小于对应最大值；runtime 账号验证、locale 五条查询、Windows 配置在 Linux 路径及连接改写的隔离模拟均通过。配置模拟复制 9 文件，Windows 服务定义仅作对照；无文件组件的运行目录由安装手册 4.1 预建。运行中的两端游戏库与服务未切换，不能把这些隔离库记作游戏实例验收。

PG17 合成样本另覆盖字段内 CR/LF/CRLF/TAB、JSON 换行、bytea、interval、浮点、分区父子表、物化视图、带引号及中文标识符；更改库/角色的渲染设置后摘要不变，行数不变而修改一个值仍能检出。读取不存在的表按受控类别拒绝，无残留 psql。
独立计数成本实测：Linux 30 万行表摘要 2.96 秒、计数 0.08 秒，占整次扫描 2.3%；Windows 20 表小库整次扫描 5.64 秒、计数语句 0.28 秒。每次备份前后各扫描一次，因此比旧工具多两轮全表计数；这些合成数据耗时不能估算正式停机窗口。

旧工具 `9b8240b` 对新格式批次的 verify 退出 0，但 restore 写入 20 张表后退出 1；因此必须先升级恢复机工具，不能以 verify 通过推定旧工具可恢复新格式。

### 2026-11-16 正式库副本迁移演练（Windows → Linux）

数据来源是对正式服只读取得的在线 `pg_dump` 与全部录像文件（未停服，未在正式服写入任何内容）。副本含真实账号数据，只保存在维护者本地与实验来宾中，不进入仓库。
源端在 Windows 来宾的隔离库按正式库的 `Chinese (Simplified)_China.936`（libc）、UTF8 重建：21 张表、3,029,587 行、13 个序列，79,473 个录像（68,347 个文件名含非 ASCII 字符，全部大小写混合）。
目标是 Linux 来宾上各自全新的内置 C.UTF-8 库和全新目录。工具为 `f6aaae0`；旧批次由 `9b8240b` 的旧工具生成。

| 步骤 | 结果 |
| --- | --- |
| Windows：旧工具联合备份 | 通过，无 `rowDigestFormat`；3,098 秒（Defender 未排除） |
| Windows：新工具联合备份 | 通过，新格式；1,169 秒（备份目录加临时路径排除） |
| 两个批次对比 | 每表行数相同；17 张非空表的摘要全部不同、4 张空表相同，与行尾差异一致；录像关联 79,466 个已关联、7 个无库记录、2 条库记录无文件 |
| `tar.exe` 打包 → Linux `tar` 解包 | 每个归档 307 MB，打包 12–13 秒、解包 8–10 秒；79,473 个文件名均为合法 UTF-8；verify 通过，67–73 秒 |

| 新批次 → Linux 新库 | 通过，新格式严格匹配，214 秒 |
| 两个目标库按新格式重新计算 | 整个 `databaseState` 相同 |
| runtime 账号 schema verify | 通过，20 张契约表，4 条 `ladder_match_game` 历史默认值警告（源库同样有） |

整库摘要扫描：Windows 来宾 55.9 秒、Linux 来宾（1 vCPU）32.2 秒；其中独立计数语句 0.36 秒与 0.26 秒，占 0.6% 与 0.8%。旧批次的双候选扫描为 41.6 秒与 34.8 秒。
以上均为实验 VM 的单次数据。Windows 备份耗时与 Defender 的关系见 [Defender 临时排除](backup-restore.md#windows文件多时的-defender-临时排除)。

演练中发现并修复：停写检查曾把 autovacuum 工作进程算作连接，大批量导入后的备份会被误拒（`f6aaae0`，判据改为只统计带登录用户的会话；真实 autovacuum 期间旧判据拒绝、新判据放行，另有真实客户端会话时新判据仍拒绝）。

**排序：中文 locale → 内置 C.UTF-8。** 2,149 个账号中 1,220 个名字含非 ASCII 字符；名字转小写后仍是 2,149 个，没有大小写冲突。两端各按同一条查询取出名字顺序后比对（只比对哈希，不导出名字）：

| 查询形态 | 位置上条目不同 | 前 10 名 | 前 100 名 | 首个差异名次 |
| --- | --- | --- | --- | --- |
| 按名字升序 | 2,147 / 2,149 | 10 | 100 | 1 |
| 积分降序、名字升序（总榜） | 1,039 / 2,149（48.3%） | 0 | 8 | 49 |
| 胜场降序、名字升序 | 1,619 / 2,149（75.3%） | 0 | 6 | 49 |
| 月份、积分降序、名字升序（月榜，全部月份串接） | 588 / 2,302（25.5%） | — | — | 37 |

排行榜的差异只发生在主排序值相同的并列条目之间（积分并列共 197 组、覆盖 1,979 个账号），并列内部按名字排，而名字顺序在两种排序规则下几乎完全不同；主排序值不同的条目先后不变。
维护者已于 2026-11-16 依据上表接受这一差异（并列玩家的先后改变，前 10 名不变）。该接受只针对本次副本数据的这四种查询形态；真正迁移时仍按 [Linux 安装 3.3](linux-install.md#33-b导入已有数据) 对当时的数据出 locale-check 并在回执写明。恢复工具不因排序规则不同而拒绝或放行。

本演练未覆盖：

- 这两个恢复库上的游戏实例与真实客户端登录、回放、新对局。
- 正式服上真实的停服联合备份及其耗时；本次源数据是在线 dump 的副本，备份在实验来宾完成。
- 实验环境限制：Windows 来宾（VirtualBox 在 Hyper-V 兼容模式下）在第一次新格式备份期间出现来宾时钟停摆，该次备份被中断，中断产物改名保留，重启后重新做了一次完整备份；上表为重做的结果。旧工具备份在时钟异常开始前后完成，其 3,098 秒只作量级参考。

### 2026-11-16 清单核对轮数优化的实测

`02fba1d`、`4eff66c`、`dfce0a4` 减少了备份、verify、恢复中重复的整轮哈希，并让同一次扫描内每个目录只检查一次链接，每个文件只查询一次状态；清单内容、顺序与格式不变。
Codex 独立审计无 P0，查出的 1 项 P1（Windows 上目录名与组件 ID 只差大小写时，虚报为空的组件清单会被接受）与 2 项 P2 已在 `4eff66c` 修复，其独立用例并入测试。

在 Windows 来宾用上面的正式库副本对比（同一次开机、源文件已读入缓存、备份目录临时排除 Defender，单次数据）：

| 操作 | 优化前（`f6aaae0`） | 优化后（`dfce0a4`） |
| --- | --- | --- |
| 联合备份 | 1,389 秒 | 585 秒 |
| 单独 verify 同一批次 | 289 秒 | 82 秒 |
| 恢复到全新库（中文 locale，Windows → Windows） | 972 秒 | 464 秒 |

- 两个工具对同一数据生成的清单完全相同：79,473 行组件文件逐项相同（含顺序），`databaseState`、录像关联、字段集合均相同。
- 新旧工具互相 verify 对方的批次都通过，旧格式批次也通过；两次恢复的三项标志均为 true，按新格式严格匹配。
- 这也是正式库副本首次完成 Windows → Windows 的全量恢复；目标库与源库同为 `Chinese (Simplified)_China.936`，排序不变。
- 计时不含 Defender 未排除的情形；重启后文件缓存为冷时，同一 verify 用了 320 秒。

## 两条演练路线

### A：全新安装

全新Linux或隔离VM → OS/Node/PG17 →release校验解包/引擎构建→新空库初始化→
runtime只读schema验证→systemd/Nginx→测试账号和完整TT/普通房→录像/统计→reboot。

结果要记录OS、CPU、Node/npm、PG客户端/服务端、代码dirty/制品SHA、引擎binarySHA、
Core/Lua/scripts/CDB/禁表指纹、域名/端口/Origin和每项失败定位。
不从开发机隐含node_modules、私有配置、原库和Windowsbinary借依赖。

### B：联合恢复

合成库产生账号/积分/Match/单局/使用率及三类录像样本 →自然排空并停所有writer→
联合backup与verify→异机复制后verify→不同名字新空库/新目录restore→
内容/序列/schema/角色/SHA/录像分类一致→路径映射→新写入→重启。

先在合成样本上证明工具，然后再由管理员在私有隔离目标上恢复一份真实批次。
全量数据体积、真实locale、现场新增表/扩展会影响耗时与兼容性；不能用几行合成样本估算正式恢复时间。
